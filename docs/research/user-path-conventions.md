# Reversible current-user PATH setup across supported systems

Research date: 2026-08-01

Scope: current-user, no-administrator installation for human-operated local terminals; automatic Bash, Zsh, Fish, Windows PowerShell/PowerShell, and cmd support; WSL treated as Linux; unsupported shells receive manual guidance. This scope comes from [research issue #11](https://github.com/flyingmt/mdvl/issues/11) and the [Binary Installer map](https://github.com/flyingmt/mdvl/issues/9). This report maps facts and alternatives. It deliberately leaves policy to [Choose install locations and PATH ownership rules](https://github.com/flyingmt/mdvl/issues/21).

## Authority labels

- **Guarantee** means behavior specified by the platform, shell, or standards owner.
- **Recommendation** means an official `should`, `may`, convention, or default, not a guarantee that a machine is configured that way.
- **Convention** means a platform-owner-designated location or usage that does not guarantee command-search behavior.
- **Common practice** means an example or typical arrangement in owner documentation, not required behavior.
- **Implication** is a conclusion for the later design ticket, not a decision made here.

## Short answer

- There is no cross-platform current-user executable directory. Linux has the XDG **recommendation** `$HOME/.local/bin`; macOS has an Apple-defined user data area but no Apple-defined per-user CLI executable directory; Windows has the per-user `FOLDERID_UserProgramFiles`, whose default is `%LOCALAPPDATA%\Programs`. [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/latest/) [Apple File System Programming Guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html) [Windows KNOWNFOLDERID](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)
- Bash and Zsh have different login and interactive startup files. Neither documents a per-user drop-in directory or third-party ownership marker, so automatic reversible edits require an mdvl-defined ownership protocol. [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html) [Zsh startup files](https://zsh.sourceforge.io/Doc/Release/Files.html)
- Fish offers two documented persistent surfaces: a user configuration tree, including `conf.d`, and universal `fish_user_paths` manipulation through `fish_add_path`. Universal variables can update running Fish instances; a config file takes effect when Fish loads it. [Fish configuration files](https://fishshell.com/docs/current/language.html#configuration-files) [Fish universal variables](https://fishshell.com/docs/current/language.html#universal-variables) [fish_add_path](https://fishshell.com/docs/current/cmds/fish_add_path.html)
- Windows User-scope environment variables are the one persistent surface shared by future PowerShell and cmd processes. The User target is `HKEY_CURRENT_USER\Environment`; the official .NET setter stores there, notifies applications with `WM_SETTINGCHANGE`, and updates running File Explorer instances for inheritance by new Explorer children. [EnvironmentVariableTarget](https://learn.microsoft.com/en-us/dotnet/api/system.environmentvariabletarget?view=net-10.0) [Environment.SetEnvironmentVariable](https://learn.microsoft.com/en-us/dotnet/api/system.environment.setenvironmentvariable?view=net-10.0) [WM_SETTINGCHANGE](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-settingchange)
- An installer launched from a shell is a child process and cannot directly alter that parent shell's environment. Unix external commands execute in a separate environment, and Windows permits direct cross-process environment changes only while a parent creates its child. Persistence affects later shells; the current shell needs a parent-executed command, restart, or a shell-owned synchronization facility such as Fish universal variables. [Bash command execution environment](https://www.gnu.org/software/bash/manual/html_node/Command-Execution-Environment.html) [POSIX `fork()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fork.html) [Windows changing environment variables](https://learn.microsoft.com/en-us/windows/win32/procthread/changing-environment-variables)

## Installation location facts

### Linux and WSL

- **Recommendation:** XDG defines user data at `$XDG_DATA_HOME` or `$HOME/.local/share`, configuration at `$XDG_CONFIG_HOME` or `$HOME/.config`, state at `$XDG_STATE_HOME` or `$HOME/.local/state`, and says user executables *may* be stored at `$HOME/.local/bin`. There is no `XDG_BIN_HOME`. XDG says distributions *should* put `$HOME/.local/bin` on `PATH`, so its presence is not guaranteed and must be checked. [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/latest/)
- **Guarantee:** Set XDG paths must be absolute; relative values are invalid and should be ignored. For a missing destination directory, the specification says to attempt creation with mode `0700`, not change permissions of an existing directory, and handle write failure. [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/latest/)
- **Recommendation caveat:** XDG warns that a home directory may be shared by machines of different architectures, making compiled files in `$HOME/.local/bin` architecture-specific. That matters to an arm64/x64 installer and receipt design. [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/latest/)
- **Scope application:** WSL should use the Linux/XDG and Linux-shell rows below, not the Windows registry. WSL can append Windows path elements to Linux `$PATH`; `appendWindowsPath` defaults to `true`, so imported duplicates and a long starting path are possible. [WSL advanced settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-config#interop-settings)

### macOS

- **Guarantee:** Apple's user domain is the current user's home directory; a home may be on the boot volume or a network volume. Apple says the current user has access to and control over files in that home, subject to filesystem permissions and ACLs. [Apple File System Programming Guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)
- **Convention:** Apple designates `~/Library/Application Support/<app-identifier>/` for app-managed, user-specific support data. This is an authoritative data/receipt candidate, not a documented command-search directory. [macOS Library Directory Details](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html)
- **Convention boundary:** Apple's directory guide identifies `~/Applications` for user-specific apps and `~/Library` for user-specific app files, but it does not identify a per-user directory for standalone command-line executables. Using `$HOME/.local/bin` on macOS would therefore adopt the XDG convention, not an Apple platform guarantee. [Apple File System Programming Guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html) [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/latest/)
- **Not a current-user mechanism:** Apple's `path_helper` reads `/etc/paths`, `/etc/paths.d`, `/etc/manpaths`, and `/etc/manpaths.d`, and says it is intended for shell profiles rather than direct invocation. Those are system paths, not a documented per-user drop-in. [Apple `path_helper(8)`](https://github.com/apple-oss-distributions/shell_cmds/blob/main/path_helper/path_helper.8)
- **Case caveat:** APFS has both case-insensitive and case-sensitive formats, so a macOS path must not be deduplicated by unconditional case-folding. [Apple Disk Utility file system formats](https://support.apple.com/guide/disk-utility/file-system-formats-available-in-disk-utility-dsku19ed921c/mac)

### Windows

- **Guarantee:** `FOLDERID_UserProgramFiles` is a per-user Known Folder whose default path is `%LOCALAPPDATA%\Programs`; `FOLDERID_LocalAppData` is a per-user Known Folder whose default is `%USERPROFILE%\AppData\Local`. These provide executable/payload and non-roaming data candidates, respectively, without choosing a final mdvl layout. [Windows KNOWNFOLDERID](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)
- **Guarantee:** Known Folders may be redirected, including to network locations, and new code should resolve them with `SHGetKnownFolderPath` rather than hard-code defaults. Passing a null token resolves the current user's folder. [Windows Known Folders](https://learn.microsoft.com/en-us/windows/win32/shell/known-folders) [SHGetKnownFolderPath](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath)
- **Permission caveat:** Registry access is ACL-controlled. Setting a registry value requires `KEY_SET_VALUE`, and opening a key fails when the caller lacks the requested access. Current-user scope avoids an administrator requirement by design, but write success is still not unconditional. [Registry key security and access rights](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights) [RegSetValueExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regsetvalueexw)

## Why the current parent shell cannot be changed

- **Guarantee, POSIX:** `fork()` gives the child its own process and copies parent state; `execve()` supplies an environment to the replacement process image. Environment names and values are process data, and arguments plus environment are bounded by `ARG_MAX`. [POSIX `fork()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fork.html) [POSIX `exec`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/exec.html) [POSIX environment variables](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html)
- **Guarantee, Bash:** An external command runs in a separate execution environment and cannot affect the shell's execution environment. Bash's `.`/`source` builtin is different because it executes a file in the current shell context. [Bash command execution environment](https://www.gnu.org/software/bash/manual/html_node/Command-Execution-Environment.html) [Bash `.` builtin](https://www.gnu.org/software/bash/manual/html_node/Bourne-Shell-Builtins.html#index-_002e)
- **Guarantee, Windows:** Each process has an environment block; a child normally inherits the parent's block. `SetEnvironmentVariableW` changes only the current process and explicitly has no effect on other processes. Windows documents child creation as the only time one process can directly set another process's environment. [Windows environment variables](https://learn.microsoft.com/en-us/windows/win32/procthread/environment-variables) [SetEnvironmentVariableW](https://learn.microsoft.com/en-us/windows/win32/api/processenv/nf-processenv-setenvironmentvariablew) [Windows changing environment variables](https://learn.microsoft.com/en-us/windows/win32/procthread/changing-environment-variables)
- **Implication:** The installer can persist configuration and print a parent-shell command, but printed text is not executed by the parent. Bash/Zsh and existing Windows shells remain stale until the user runs a shell-native command or starts a process from a refreshed ancestor. Fish universal variables are a documented shell-managed exception: `set --universal` is immediately available to the user's Fish instances and persists across Fish restarts. [Fish `set`](https://fishshell.com/docs/current/cmds/set.html)

## Shell startup and persistent PATH surfaces

### Bash

- **Guarantee:** An interactive login Bash reads `/etc/profile`, then only the first readable file among `~/.bash_profile`, `~/.bash_login`, and `~/.profile`. An interactive non-login Bash reads `~/.bashrc`. Non-interactive Bash uses `BASH_ENV`; Bash invoked as `sh` follows different rules. [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)
- **Common practice, not guarantee:** The Bash manual says a login profile *typically* sources `~/.bashrc`; it does not require that arrangement. Editing only `~/.profile` can be shadowed by `~/.bash_profile` or `~/.bash_login`, while editing only `~/.bashrc` misses login shells that do not source it. [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)
- **Implication:** For human local terminals, `BASH_ENV` is out of scope. The later policy must select files for both login and interactive non-login coverage and define whether missing files are created; no single documented Bash user file covers both modes unconditionally. [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)

### Zsh

- **Guarantee:** Zsh reads `$ZDOTDIR/.zshenv` for normal invocations, `$ZDOTDIR/.zprofile` for login shells, and `$ZDOTDIR/.zshrc` for interactive shells; `$ZDOTDIR/.zlogin` is a later login file. If `ZDOTDIR` is unset, it uses `HOME`. `RCS`/`GLOBAL_RCS` can suppress later startup files. [Zsh startup files](https://zsh.sourceforge.io/Doc/Release/Files.html)
- **Scope caveat:** `.zshenv` reaches non-interactive shells as well as human terminals, while `.zprofile` and `.zshrc` divide login and interactive behavior. The later policy must decide whether to touch both human-facing files and how to resolve a non-default `ZDOTDIR`. [Zsh startup files](https://zsh.sourceforge.io/Doc/Release/Files.html)
- **macOS convention:** Apple says zsh is the default login and interactive shell for new accounts since macOS 10.15, describes `.zprofile` as login-time and `.zshrc` as per new Terminal session, and does not say this eliminates Zsh's own mode distinctions. [Apple zsh support article](https://support.apple.com/102360)

### Fish

- **Guarantee:** Fish reads user configuration from `$XDG_CONFIG_HOME/fish` or `~/.config/fish`, including `config.fish` and `conf.d/*.fish`; configuration is read for every Fish startup, and `status is-interactive`/`status is-login` can gate mode-specific code. [Fish configuration files](https://fishshell.com/docs/current/language.html#configuration-files) [Fish `status`](https://fishshell.com/docs/current/cmds/status.html)
- **Guarantee:** `fish_add_path` normally adds normalized, existing directories to `fish_user_paths`, does not add an already included directory, prepends by default, and uses a universal variable by default when no prior scope dictates otherwise. A one-time universal change persists; `--path` or global scope does not persist unless put in configuration. [fish_add_path](https://fishshell.com/docs/current/cmds/fish_add_path.html)
- **Guarantee:** Fish list variables permit erasing one indexed element, and universal variables are immediately shared with the user's Fish instances and persisted across restarts. This allows entry-level removal without deleting unrelated `fish_user_paths` values. [Fish `set`](https://fishshell.com/docs/current/cmds/set.html) [Fish universal variables](https://fishshell.com/docs/current/language.html#universal-variables)
- **Ownership caveat:** If the directory was already present, `fish_add_path` makes no change, so mdvl must not later claim or remove that pre-existing entry. If `fish_user_paths` already has a different scope, `fish_add_path` follows it; therefore universal-variable behavior cannot be assumed without inspecting scope. [fish_add_path](https://fishshell.com/docs/current/cmds/fish_add_path.html) [Fish `set --show`](https://fishshell.com/docs/current/cmds/set.html)
- **Alternative boundary:** A uniquely named user `conf.d` file can be wholly installer-owned, but Fish loads configuration at startup and a same-named file can mask another configuration file in its search path. The later policy must choose between an owned fragment, universal entry, or shared `config.fish` edit. [Fish configuration files](https://fishshell.com/docs/current/language.html#configuration-files)

### Windows User environment, PowerShell, and cmd

- **Guarantee:** Windows has Machine, User, and Process environment scopes. Process scope is inherited from the parent and is constructed from Machine/User values; a normal PowerShell `$Env:Path` assignment or cmd `set` changes only the current process/session. [PowerShell environment variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables?view=powershell-7.5) [cmd `set`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/set_1)
- **Guarantee:** The User target maps to `HKEY_CURRENT_USER\Environment`. `Environment.GetEnvironmentVariable(name, User)` reads that User value rather than the already-combined current process value; this distinction avoids copying Machine PATH entries into User PATH. [EnvironmentVariableTarget](https://learn.microsoft.com/en-us/dotnet/api/system.environmentvariabletarget?view=net-10.0) [Environment.GetEnvironmentVariable](https://learn.microsoft.com/en-us/dotnet/api/system.environment.getenvironmentvariable?view=net-10.0)
- **Guarantee:** `Environment.SetEnvironmentVariable(name, value, User)` persists in `HKEY_CURRENT_USER\Environment`, notifies applications with `WM_SETTINGCHANGE`, copies the update to running File Explorer instances, and lets new Explorer-launched processes inherit it. It does not update the calling process's environment block. [Environment.SetEnvironmentVariable](https://learn.microsoft.com/en-us/dotnet/api/system.environment.setenvironmentvariable?view=net-10.0) [EnvironmentVariableTarget](https://learn.microsoft.com/en-us/dotnet/api/system.environmentvariabletarget?view=net-10.0)
- **Guarantee for direct registry writes:** A writer can query and set a registry value with an explicit type; `REG_EXPAND_SZ` preserves unexpanded `%NAME%` references while `REG_SZ` is a plain string. After changing User or system environment values directly, Windows says to broadcast `WM_SETTINGCHANGE` with `lParam = "Environment"`; listeners decide when to reload. [Registry value types](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-value-types) [RegSetValueExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regsetvalueexw) [WM_SETTINGCHANGE](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-settingchange)
- **PowerShell profile limitation:** Profiles are host- and edition-specific, can be skipped with `-NoProfile`, and can be blocked by execution policy. Windows PowerShell 5.1 uses `$HOME\Documents\WindowsPowerShell\Profile.ps1`; PowerShell 7 uses `$HOME\Documents\PowerShell\Profile.ps1`. A profile edit would not configure cmd. [Windows PowerShell 5.1 profiles](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_profiles?view=powershell-5.1) [PowerShell 7 profiles](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_profiles?view=powershell-7.5)
- **cmd AutoRun limitation:** cmd can execute an HKCU `Command Processor\AutoRun` value, but `cmd /d` disables it. AutoRun is cmd-only, so it is not a common PowerShell/cmd PATH surface. [cmd](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmd)
- **`setx` warning:** `setx` writes future command-window values, not the current window, expands embedded variable references, and crops assigned data beyond 1024 characters. Those documented transformations can lose unrelated PATH data. [setx](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/setx)

## Reversibility and ownership implications

- **Shared Unix profiles:** Bash and Zsh specify which files they execute, not an installer ownership format. A bounded marker block and installer receipt would be an mdvl protocol. Issue #21 must decide whether uninstall requires a byte-for-byte block match and what to do with a missing, duplicate, or user-edited marker. [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html) [Zsh startup files](https://zsh.sourceforge.io/Doc/Release/Files.html)
- **Profile-file identity:** POSIX `stat` exposes owner and mode, while `lstat` distinguishes a symbolic link from its target. Shell docs require readability but do not guarantee that a discovered profile is a regular, current-user-owned, writable file. The policy must define refusal/manual-guidance behavior for symlinks, wrong ownership, ACL denial, non-regular files, and generated/dotfile-managed content. [POSIX `stat`/`lstat`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/stat.html) [POSIX file access permissions](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap04.html#tag_04_07) [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)
- **Fish:** An installer-created, collision-checked `conf.d` file gives a whole-file ownership unit. A universal-variable route gives a list-element ownership unit only when mdvl actually inserted it; Fish supports indexed erase. [Fish configuration files](https://fishshell.com/docs/current/language.html#configuration-files) [Fish `set --erase`](https://fishshell.com/docs/current/cmds/set.html)
- **Windows:** User `Path` is one registry value and Windows exposes no per-segment ownership primitive in the cited APIs. A receipt must at least distinguish "entry already existed" from "mdvl inserted this exact token"; uninstall must re-read current User `Path` and preserve unrelated changes rather than blindly restore an installation-time snapshot. [EnvironmentVariableTarget](https://learn.microsoft.com/en-us/dotnet/api/system.environmentvariabletarget?view=net-10.0) [RegSetValueExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regsetvalueexw)
- **Value representation:** A direct Windows registry implementation can preserve whether User `Path` is `REG_SZ` or `REG_EXPAND_SZ`; `setx` instead expands references. Whether a high-level setter's representation is acceptable, or direct typed registry access is required, remains a policy/implementation question. [Registry value types](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-value-types) [setx](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/setx)

## PATH ordering, duplicates, case, and length

- **Ordering:** POSIX searches `PATH` prefixes from beginning to end; Bash likewise searches each element, and cmd searches the current directory before PATH and then PATH entries in listed order. PowerShell resolves aliases, functions, and cmdlets before external executables. Prepend versus append therefore changes shadowing behavior and must be decided together with the map's "refuse to replace an mdvl executable not owned by the Binary Installer" rule. [POSIX `PATH`](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html#tag_08_03) [Bash command search](https://www.gnu.org/software/bash/manual/html_node/Command-Search-and-Execution.html) [cmd path](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/path) [PowerShell command precedence](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_command_precedence?view=powershell-7.5)
- **Duplicates:** Fish documents normalization and duplicate avoidance in `fish_add_path`; Bash/Zsh profile assignments and the Windows User `Path` registry value have no cited automatic deduplication contract. Repeated startup evaluation can therefore duplicate an unguarded Bash/Zsh entry, while Windows insertion must parse semicolon-separated entries itself. [fish_add_path](https://fishshell.com/docs/current/cmds/fish_add_path.html) [Bash environment](https://www.gnu.org/software/bash/manual/html_node/Environment.html) [PowerShell PATH separators](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables?view=powershell-7.5#path-information)
- **Case:** POSIX environment names and filenames preserve upper/lowercase identity; Windows environment names are case-insensitive. Native Windows path APIs normally treat path case as equivalent, but NTFS directories can be case-sensitive; macOS APFS can also be case-sensitive. A single cross-platform lowercasing rule is unsafe. [POSIX environment variables](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html) [POSIX filenames](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap04.html#tag_04_09) [.NET environment lookup](https://learn.microsoft.com/en-us/dotnet/api/system.environment.getenvironmentvariable?view=net-10.0) [Windows file naming](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file) [Apple APFS formats](https://support.apple.com/guide/disk-utility/file-system-formats-available-in-disk-utility-dsku19ed921c/mac)
- **Other semantic duplicates:** Windows can preserve long names while also exposing 8.3 aliases, and registry `REG_EXPAND_SZ` can represent a path through `%VARIABLE%`; Unix symbolic links can provide multiple pathnames to one directory. Exact-string, normalized-string, and same-directory tests therefore have different ownership consequences. [Windows file naming](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file) [Registry value types](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-value-types) [POSIX pathname resolution](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap04.html#tag_04_16)
- **Unix length:** POSIX gives no standalone fixed maximum for `PATH`; arguments plus environment are limited by runtime `ARG_MAX`, queryable through `sysconf(_SC_ARG_MAX)`, and `exec` can fail with `E2BIG`. [POSIX environment variables](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html) [POSIX `sysconf`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/sysconf.html) [POSIX `exec`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/exec.html)
- **Windows length:** Win32 documents a 32,767-character maximum for a user-defined environment variable. cmd-specific Microsoft pages are inconsistent: the troubleshooting article says 8,191 characters and says cmd ignores inherited variables above that limit, while the current cmd reference states 8,192 bytes per variable and 65,536 characters total. `setx` independently crops at 1,024 characters. The specification must choose a conservative supported limit or add an acceptance test rather than silently truncate. [Windows environment variables](https://learn.microsoft.com/en-us/windows/win32/procthread/environment-variables) [cmd length troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation) [cmd reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmd#setting-environment-variables) [setx](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/setx)
- **Separators:** POSIX PATH uses `:` and a zero-length component denotes the current directory; Windows uses `;`. Empty segments and user formatting must not be casually normalized because they can change command search behavior. [POSIX `PATH`](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html#tag_08_03) [PowerShell PATH information](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables?view=powershell-7.5#path-information)

## Permissions and unsupported shells

- **Executable permission:** POSIX PATH search requires an executable file with appropriate execution permission. XDG's missing-directory guidance is mode `0700`; existing directory permissions must not be rewritten merely to fit the installer. [POSIX `PATH`](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html#tag_08_03) [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/latest/)
- **macOS permissions:** Apple documents both BSD permissions and ACLs as governing filesystem access, including user-home content. A nominally per-user path is not a promise that every target/profile write will succeed. [Apple File System Programming Guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html#//apple_ref/doc/uid/TP40010672-CH2-SW13)
- **Windows permissions:** User-scope APIs can still return permission/security failures, and registry writes require `KEY_SET_VALUE`. Failure must lead to no-admin recovery/manual guidance, not elevation or a machine-scope fallback. [Environment.SetEnvironmentVariable exceptions](https://learn.microsoft.com/en-us/dotnet/api/system.environment.setenvironmentvariable?view=net-10.0) [Registry key security](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights)
- **Unsupported shell detection:** POSIX defines `SHELL` as the user's preferred command interpreter, not as proof of the currently executing shell. Because startup filenames and syntax are shell-defined, unsupported shells need manual instructions naming the selected directory, explaining persistence/current-session limits, and directing the user to that shell's startup documentation; the installer cannot safely guess a profile. [POSIX `SHELL`](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html#tag_08_03) [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html) [Zsh startup files](https://zsh.sourceforge.io/Doc/Release/Files.html) [Fish configuration files](https://fishshell.com/docs/current/language.html#configuration-files)
