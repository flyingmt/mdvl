# The daemon serves pictures from the Project Root

A rendered document points at files beside itself, and until now every such address came back as the reviewer app's shell — a `200` the browser cannot decode and nothing logs as an error. So the last stop in the router looks into the Project Root before it falls back to that shell: a request whose path canonicalises to a file under the root and whose name ends in one of seven picture extensions is answered with that file's bytes. Nothing else moves. The embedded app still wins the address if it holds one, and an address that names no picture still gets `index.html`, which is the only reason a review's deep link resolves at all.

That path goes through the check every other request goes through rather than a second one written for this route: `ProjectRoot::resolve` was split so `file_inside` holds the canonicalise-and-`starts_with` guard while `resolve` adds the markdown gate the CLI still needs, and both callers keep the guard they had. `.mdvl/` is refused as a directory, whatever a file inside it happens to be called, because that is where the daemon's token and the Comments a human wrote are kept. The content type is read off the name against a fixed list and never off the bytes, and `X-Content-Type-Options: nosniff` goes out beside it. The fallback route now carries `only_from_us`, which it never did while everything it served was compiled into the binary.

## Considered Options

Serving only what a rendered document references sounds narrower and is not one: the daemon cannot work out that list, because [0001](./0001-markdown-parsing-in-the-browser.md) keeps the markdown parser in the browser, and a list the browser uploads is a convenience filter rather than a boundary — any process on the machine can send its own. It would also hand a view something to register with the daemon, which [reusing-tabs-for-views](../../.out-of-scope/reusing-tabs-for-views.md) rules out by design.

An `<img>` cannot carry the daemon's token, so authenticating these requests properly would mean a second credential. A cookie planted alongside the token at `/api/exchange` would be sent automatically and would genuinely work, at the price of a second place the secret lives beside the `localStorage` that [0005](./0005-a-ticket-opens-the-browser.md) chose, with its own lifetime and its own answer for a stale entry after a restart. A signed query token per path is stronger still and is plainly a second scheme, which issue #1 puts out of scope along with any authentication beyond the daemon token. Neither was taken; `only_from_us`, the refusal of `.mdvl/`, and the list of extensions are the whole of it.

Announcing each file's real type was ruled out before it could be weighed. An `.html` file under the root, answered as `text/html`, runs script on the origin whose `localStorage` holds the token — the render pipeline strips raw HTML out of the document for exactly that reason, and the HTTP layer must not hand it back. SVG stays off the list on the same ground and one more: diagrams are drawn by mermaid in the browser, so a picture on disk is rarely a diagram. Reopen SVG when a document actually needs one, and only together with `Content-Security-Policy: default-src 'none'` on the response.

## Consequences

`only_from_us` is not authentication and does not become it here. It turns away a cross-origin `fetch` and a DNS rebind, but an `<img>` sends no `Origin` at all, so the check passes for our tab and a stranger's alike. Three exposures follow, and they are accepted rather than overlooked. Any other local process, including one run by another user of the machine, that can reach the port can read any file under the Project Root whose name ends in one of the seven extensions. A hostile tab in the reviewer's own browser can point an `<img>` at a path and learn from `onload` and `onerror` whether that file exists and how large it is, though the pixels themselves stay unreadable across origins. And what all of that opens is the pictures in someone's repository — that is the extent of it. The token in `.mdvl/daemon.json` and a human's Comments in `.mdvl/results/<id>.json` are out of reach through the directory refusal and the list both, and `tests/cli.rs` holds that pair down.

Serving the bytes is only half of what makes a picture appear. Neither `/v` nor `/r/<id>` is where the document lives, and `/r/<id>` is a segment deeper besides, so a relative address in the document is rewritten against the document's own directory before the browser is ever asked for it. That half is in [the reviewer's app](../design/reviewer-app.md).
