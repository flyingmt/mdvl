# The daemon exits when the last Review ends

The daemon used to outlive its work by up to thirty idle minutes, and a `mdvl wait` that polled after any exit got only "no review daemon is running". Now, when a Submit or Cancel leaves no Review that still needs the daemon, it announces the change, waits 150ms for in-flight responses to land, checks once more, and exits. Every terminal transition — Submit, Cancel (including one driven by shutdown), Conflict — persists the Review's Outcome to `<root>/.mdvl/results/<id>.json`, delegating to the same atomic temp-file-and-rename write Submit uses for the document itself. A `mdvl wait` that cannot get an answer from the daemon — it may never have connected, or the daemon may have died between connecting and answering — reads that file, prints exactly the bytes the daemon would have answered, and deletes the file only once the answer is out; a live daemon that delivers an Outcome over HTTP deletes the file too.

This does not break ADR 0003's invariant that Review state stays alive between `wait` calls — it extends the medium that holds it. A pending Review still lives only in the daemon's memory, and the daemon still never exits while one is pending, so polling a live daemon is unchanged. What changes is that a terminal Outcome no longer needs a live daemon to reach the Agent: it waits on disk until delivered once. And if the persist itself fails, the daemon is the only channel left — so a Review whose Outcome never reached the disk still counts as needing the daemon, and no exit fires while one does. Both exits live in `retire` and ask the same predicate: `if_drained` after a Submit or Cancel and `when_idle` on the thirty-minute clock both go through `needed`, which holds while any Review is open or its Outcome is not yet safely on disk.

Nor is this the "Review history or persistence across daemon restarts" that issue #1 leaves out of scope. It is not history — nothing enumerates past Reviews and nothing is retained, since the file is deleted as it is delivered. It is not persistence of Reviews — a pending Review never touches the disk and still dies with its daemon. Only the terminal Outcome crosses the boundary, because the Agent is owed the answer the human already gave even when the daemon has rightly exited.

## Considered Options

Staying idle-only keeps a process around after its work is done — the complaint behind story 41. Exiting without persisting loses the human's answer whenever `wait`'s next poll lands after the exit, reintroducing the lost-answer race the non-blocking CLI exists to avoid. Persisting without delete-on-read accumulates an archive of past Reviews — history under another name — and lets a stale file answer a later `wait`.

## Consequences

The disk fallback is invisible to the Agent: same JSON schema, same exit codes, whether the bytes came from the daemon or the disk. The review id becomes a file name, so `wait` refuses any id that is not alphanumeric or underscore before touching the disk. The `results/` directory inherits the per-root `.mdvl/.gitignore`, so nothing new shows up in a user's repository. The automatic exit, unlike the manual shutdown, re-checks that no Review needs the daemon after the 150ms grace — a new Review can land in that window and the daemon must not die out from under it.
