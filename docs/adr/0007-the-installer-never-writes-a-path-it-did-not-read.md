# The installer never writes a PATH it did not read

`configureWindowsPath` and `removeWindowsPath` build one PowerShell script and run it as a single `powershell.exe -NoProfile -NonInteractive -EncodedCommand` child through `execFileSync` with `shell: false`. The read, the decision and the write all happen inside that script and only a short ASCII status token comes back, so the User PATH never travels on a command line or through stdout — the channel that four of the six documented ways mdvl 0.1.x destroyed a PATH came in through: `cmd` expanding `%USERPROFILE%` before `reg` saw it, a trailing backslash escaping the closing quote of `/d "…\"`, `&` and `^` read as metacharacters, and cp949 stdout decoded as UTF-8. The read is `RegistryKey.GetValue(name, $null, 'DoNotExpandEnvironmentNames')`, so `%USERPROFILE%` stays a reference; the write is `RegistryKey.SetValue(…, RegistryValueKind::ExpandString)` — always `REG_EXPAND_SZ`, never a type inferred from whether the value happens to contain a `%`. `Get-ItemProperty` and `[Environment]::GetEnvironmentVariable` expand on read and `[Environment]::SetEnvironmentVariable` stores `REG_SZ`; either one freezes one machine's absolute paths into a value that was portable (rustup#261). `powershell.exe` rather than `pwsh`, because 5.1 ships with every supported Windows and this runs before anything of ours is on the PATH.

The other two destruction paths were one policy twice — a read that failed became an empty string, and the empty string was written. So nothing is written now unless a value was first read successfully. An absent value is not an unreadable one: a user who never had a User PATH gets one created, while an unexpected value kind, a null read, or any exception in the script leaves the registry exactly as found. That distinction is rustup's; pnpm collapses both into a refusal and we do not. Refusing to write is not failing the install — the step returns `skipped Windows User PATH (<token>)` carrying the directory to add by hand, and the caller prints it as a warning beside a binary that is already in place. The 2048-character limit that used to `throw` here is gone: it guarded a `setx` this code never calls, `mdvl.js` never caught it, and it unwound a finished install — binary and receipt already written — into `Exit 1`.

The uninstall gets the same rules rather than the ones it happened to survive on: same read, same kind check, same refusals, same `REG_EXPAND_SZ` write. Every entry that is not mdvl's own is kept byte for byte — empty segments, trailing backslashes and `%VAR%` references belong to whoever put them there — and normalization is used only to recognize mdvl's own entry. A removal that empties the value deletes it instead of storing `""`. Nothing backs up the original: not the receipt, not a file, and uninstall restores nothing.

## Considered Options

`execFileSync('reg', …)` is the smallest change that drops the shell, and it does close the expansion, quoting and metacharacter paths — but the value still crosses stdout to be parsed in Node, and `reg query`'s output format and encoding are unspecified by Microsoft. pnpm, on that same mechanism, has to wrap it in `chcp 65001` to survive. A native addon such as `native-reg` would read in-process with no text round trip at all, but the installer has zero runtime dependencies and five platform packages would inherit a prebuild burden for one function. A subcommand on the mdvl binary is impossible on the way out — `mdvl.js` deletes the binary before it cleans the PATH — and on the way in it would make PATH correctness depend on the thing being installed. A backup taken before writing was considered and rejected: none of the seven installers surveyed keeps one, because a writer that never writes a value it did not read leaves nothing to roll back. What a backup mostly does is make it feel acceptable to be less careful about the read, which is the only thing protecting the value.

## Consequences

Every Windows install and uninstall now starts a PowerShell process, and the `WM_SETTINGCHANGE` broadcast folded into the end of the same script compiles a small P/Invoke through `Add-Type`, costing a second or two. Broadcasting directly rather than through a throwaway User variable keeps this writer from touching any key other than the one it was handed — which matters because both functions take an `hkcuSubkey` argument so the destructive cases can run against a scratch key instead of the real `HKCU\Environment`. A syntax error in the script is indistinguishable from an unreadable registry — both come back as a skip — so the worst outcome is an install that finishes with the User PATH untouched and a warning the user has to act on. `CONTEXT.md` still describes the Binary Installer as putting the executable on the command search path; that stays the intent, and this exception joins the two already there for an undetected shell and an unwritable fish `conf.d`.

Constrained Language Mode is a sharper edge than that. A locked-down enterprise PowerShell policy forbids reaching arbitrary .NET types, so `[Microsoft.Win32.Registry]::CurrentUser` never resolves and the whole script dies as `SKIP:ERROR`. Nothing is destroyed — fail-closed holds — but the `reg.exe` call this replaces did work under CLM, so on those machines the PATH now goes unset where it used to be set. There is no `reg.exe` fallback and there will not be one: a fallback reopens the exact channel this decision closed, and every corruption case comes back with it on whichever machines take that path. A CLM user adds the directory by hand, as the warning tells them to.
