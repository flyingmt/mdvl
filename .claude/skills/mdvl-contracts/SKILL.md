# mdvl-contracts

이 프로젝트의 결정은 다섯 곳에 흩어져 있고, 각각 다른 것을 규정한다. 작업 전에
전부 읽는다 — 하나를 건너뛰면 그 축에서 이탈이 난다.

## 어디에 무엇이 있나

| 파일 | 규정하는 것 | 언제 갱신하나 |
|---|---|---|
| `CONTEXT.md` | 도메인 용어 9개와 각각의 `_Avoid_` 목록 | 새 개념이 생기거나 용어가 바뀔 때 |
| `docs/adr/*.md` | 되돌리기 어렵고, 놀랍고, 진짜 트레이드오프가 있던 결정 | 세 조건이 **모두** 참일 때만 |
| `docs/design/reviewer-app.md` | 리뷰어 화면의 결정과 근거 | UI가 바뀔 때 — 같은 변경 안에서 |
| `.out-of-scope/*.md` | **안 만들기로 한 것**과 재론 조건 | 기능 요청을 기각할 때 |
| GitHub issue #1 | 원 스펙 — 유저스토리 42개, 구현·테스트 결정, 범위 밖 | 스펙 자체가 틀렸을 때 (코멘트로) |

`CLAUDE.md`의 규칙 20개는 이 다섯과 별개로 항상 적용된다.

## 순서: 만들기 전에 기각을 확인한다

기능 요청을 받으면 **먼저 `.out-of-scope/`를 읽는다.** 이미 논파된 것이면 다시
논의하지 말고 그 파일이 정한 재론 조건이 충족됐는지만 본다.

현재 기각된 것: 다크모드, 코드펜스 문법 강조, 언어 선택 UI, 드래그 순서변경.
각 파일에 "무엇이 바뀌면 재론 가능한가"가 적혀 있다.

`docs/agents/domain.md`가 모든 스킬에게 이 디렉토리를 읽으라고 지시한다.

## 글로서리를 어긴다는 것

`CONTEXT.md`는 용어마다 쓰지 말아야 할 동의어를 명시한다. 이게 형식이 아닌
이유는 코드가 실제로 어긋난 적이 있기 때문이다 — `Review::accept()`와
`Review::park()`이 각각 Submit과 Conflict 상태를 세팅했다. 리뷰가 잡아
`submit()` / `conflict()`로 고쳤다.

용어(피해야 할 말): **Agent**(client, caller) · **Skill**(command, hook) ·
**Review**(session, task) · **Block**(node, section, chunk) ·
**Comment**(note, feedback, annotation) · **Project Root**(workspace, repo) ·
**Submit**(save, finish, done, approve) · **Cancel**(abort, reject) ·
**Conflict**(stale, dirty, race)

새 개념에 이름을 붙이기 전에 글로서리에 이미 있는지 본다. 없으면 신호다 —
프로젝트가 쓰지 않는 언어를 발명하고 있거나(재고), 진짜 빈칸이거나(추가).

## ADR을 쓸 때와 안 쓸 때

세 조건이 **전부** 참일 때만 쓴다:

1. 되돌리기 어렵다
2. 맥락 없이 보면 놀랍다 — 미래의 독자가 "왜 이렇게 했지"라고 물을 것
3. 진짜 대안이 있었고 이유가 있어 하나를 골랐다

하나라도 빠지면 안 쓴다. 쉽게 되돌릴 수 있으면 그냥 되돌리면 된다. 놀랍지
않으면 아무도 안 묻는다. 대안이 없었으면 기록할 결정이 아니다.

현재 5건: 브라우저에서 마크다운 파싱 · 수동 Skill로만 리뷰 시작 · 논블로킹
CLI + 폴링 · Project Root당 데몬 1개 · 티켓으로 브라우저 열기.

**파일명에 `token`, `secret`, `key`, `password`를 넣지 않는다.** 도구들이
민감파일로 오탐한다. ADR-0005가 실제로 그래서 지식 그래프에서 통째로 빠졌다.

## 문서 갱신은 같은 변경 안에서

나중에 하겠다는 문서는 안 써진다. 이 프로젝트에서 설계 문서가 코드와 모순된
채 **같은 커밋에** 들어간 적이 있다 — 문서는 "확인은 인라인, 모달 금지"라고
적혀 있었고 코드는 Dialog를 썼다.

갱신했으면 그 문장이 **지금 코드와 맞는지** 다시 읽는다. 갱신했다는 사실이
정확하다는 뜻은 아니다.

## 이탈이 발견됐을 때

코드가 문서와 다르면 **어느 쪽이 틀렸는지 단정하지 않는다.** 둘 다 가능하다:

- 코드가 틀렸다 → 코드를 고친다
- 문서가 낡았다 → 문서를 고친다. 되돌리기 어려운 결정이 바뀐 거면 ADR을 쓴다

근거(양쪽 인용)를 들고 사람에게 올린다. 실제로 두 경우가 다 있었다 — 글로서리
위반은 코드를 고쳤고, "모달 금지"는 문서를 고쳤다.

## 스펙 가져오기

```bash
gh issue view 1
```

`docs/agents/issue-tracker.md`가 이 레포의 이슈 규약을 정한다. 스펙을 못 가져오면
로컬 문서만으로 진행하되, **스펙 축 검증이 빠졌음을 명시한다.** 조용히 넘어가지
않는다.

## 협업

`domain-modeling` 스킬이 CONTEXT.md와 ADR을 **어떻게** 쓰는지(형식·템플릿)
규정한다. 이 스킬은 이 프로젝트에서 **어디에·언제·왜** 쓰는지를 더한다.
